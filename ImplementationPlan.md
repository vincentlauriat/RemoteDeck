**T3.2 done criterion, measurable form.** "120 Hz on a static desktop with CPU < 25 %" means:
(1) static desktop, no updates: **0 draws** (the display link is paused) and process CPU well under 25 % of one core;
(2) `-FramebufferDebug stream` (a 200 × 200 region repainted 120 times per second): draws at the display's maximum
rate (120 Hz on ProMotion, 60 Hz elsewhere) with CPU < 25 % of one core. Measured from `ps -o cputime=` deltas
over 5 s and the debug window's `draws/s` lines. Still to be measured live on an unlocked session (the first
measurement ran with the screen locked, so no frame could be drawn); 120 Hz needs a ProMotion display.

**T4.1 status.** Implemented and unit-tested. RFBKit: legacy ClientCutText/ServerCutText (Latin-1, LF; characters outside Latin-1 sent as `?`, as TigerVNC does), and the Extended Clipboard pseudo-encoding (advertised in `Encoding.preferred`): caps answered with the client's caps (text, request/peek/notify/provide, 1 MiB), server notify → request, request/peek answered from the text last shared, provide (UTF-8, CR LF, NUL) both ways, unsolicited provide within the server's text limit and a notify otherwise; Latin-1 fallback when no caps arrive. Hostile input: extended messages over 2 MiB skipped unbuffered (S32 length, `Int32.min` included), inflate capped at 1 MiB + 4 KiB, sizes checked against the data, malformed messages dropped without ending the session. App: `ClipboardBridge` per session (TRD › Clipboard), honouring `Machine.sharedClipboard` and a session-only toolbar toggle, "Clipboard too large" toast. Tests: `ClipboardVectors` from `generate_clipboard_vectors.py` (Python `zlib`, complete and sync-flushed streams, hostile cases), loopback both ways on the Latin-1 and extended paths and with sharing off (`ClipboardLoopbackTests`), `ClipboardBridgeTests` and two `SessionModelTests` on an in-memory pasteboard; fail-proofs for the Latin-1 encoding, the provide parse, the echo guard, the concealed marker and sharing off. Live (2026-10-23, reference container, scratch probe on RFBKit, Tk as the X clipboard owner, no macOS pasteboard): x11vnc 0.9.16 (libvncserver 0.9.13) sends no Extended Clipboard caps, so the Latin-1 path is used; ASCII goes both ways (CLIPBOARD and PRIMARY, ≈ 0.6–1.8 s including `docker exec`); remote non-ASCII arrives as `e?` for `é` and `?` for `€` (cause not isolated: x11vnc's conversion or the container's C locale); local `é` arrives as the right Latin-1 byte for X `STRING` requests, but x11vnc hands the same byte to `UTF8_STRING` requests (mojibake in UTF-8 apps); no echo seen. Review fixes (2026-10-23): the echo guard no longer drops a remote copy of the last shared text after a local copy elsewhere; echoes compared with the form the server holds (`ClipboardShare.sent(echo:)`); remote text before the first frame kept; reserved flag bits masked; no provide over the server's limit without notify ("Clipboard too large"); lone CR as a line end both ways; a fresh clipboard chain per connect; each with a test and a fail-proof. Acceptance criterion 5 is **not** verified on minim6 yet (Vincent: ⌘C/⌘V both ways, accented text and emoji, whether Apple's server sends caps, a password-manager copy not sent, the macOS pasteboard-privacy prompt, expected on the first programmatic read per `NSPasteboard.AccessBehavior`).
